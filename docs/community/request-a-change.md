nimpress grows by the use cases its users bring. A change request that starts with the problem, not the solution, gets discussed and shipped fastest.

## Before creating an issue

1. Search the docs and the [changelog](/changelog); the capability may exist under another name.

2. Check the [page types](/page-types) and the [authoring](/authoring) pages, which cover the surfaces most requests touch.

3. Ask whether the change belongs in nimpress or in the site: a visual choice is often a token override in the site stylesheet, see [Theming](/theming).

## Issue template

### Context

Where you are and what you are trying to do, in a paragraph. The site, the audience, the page type.

### Description

The change, as a behavior the reader would see. What renders, what a field does, what a command prints.

### Related links

Pages of this site, other tools that do it, and prior requests.

### Use cases

Two or three concrete situations where the change helps, with the page or the site that would use it.

### Visuals

A sketch, a screenshot from another site, or a mockup when the change is visual.

## Checklist

1. The problem is described before the solution.

2. The use cases are concrete.

3. The request names one change, not a list.
